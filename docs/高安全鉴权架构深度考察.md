# 前端面试：高安全鉴权架构深度考察

这份文档基于真实的 **Vue 3 + TypeScript + Dual Token + WebSocket** 架构，模拟腾讯前端 T9+ 级别的技术考察流程。

---

## 1. 基础能力验证层：从 HTTP 到双 Token 闭环
**考察维度**：`HTTP 协议`、`Promise 异步控制`、`Web 安全攻防`

### Q1.1: 为什么选择 "双 Token" 架构？Access Token 放在 Pinia 里安全吗？
**考察点**：XSS 与 CSRF 的防御边界。
**参考答案 (Rating: S)**：
- **Access Token (内存/Pinia)**：防御 CSRF（攻击者无法读取 JS 内存），但需防 XSS（通过 CSP、转义等）。
- **Refresh Token (HttpOnly Cookie)**：防御 XSS（JS 无法读取），需防 CSRF（设置 `SameSite: Strict`）。
- **S 级补充**：如果 Access Token 存 localStorage，一旦发生 XSS，攻击者可永久接管账户；存内存则攻击者必须在用户在线时实时攻击，大大压缩了攻击窗口。

### Q1.2 [手写代码]: 请实现 `ensureAuthReady` 逻辑，要求解决并发请求导致的 "Refresh Token 风暴"。
**考察点**：`Promise` 单例模式、竞态条件处理。
**参考答案 (Rating: S)**：
候选人需写出类似 `src/auth/refresh.ts` 的逻辑：
```typescript
let refreshPromise: Promise<string | null> | null = null;

export async function ensureAuthReady() {
  // 1. 内存中已有有效 Token，直接返回
  if (store.accessToken) return store.accessToken;

  // 2. 正在刷新中，返回现有的 Promise (关键点：单例)
  if (refreshPromise) return refreshPromise;

  // 3. 开启新刷新
  refreshPromise = axios.post('/refresh').then(res => {
     store.setToken(res.data);
     return res.data;
  }).finally(() => {
     refreshPromise = null; // 4. 结束后清理
  });

  return refreshPromise;
}
```

### 3 个连环追问 (Follow-up)
1.  **Q**: 如果刷新接口响应 400（Invalid Grant），前端应该怎么做？
    *   **A**: 必须立即执行 `logout()` 清理所有状态并跳转登录页，防止死循环。
2.  **Q**: 在 SSR 场景下，`authStore` 的 Token 如何初始化？
    *   **A**: SSR 服务端需读取 Cookie，通过 `pinia.state.value` 注水 (Hydration) 到客户端，或者首屏不带 Token，由客户端 `onMounted` 后懒加载。
3.  **Q**: 如何实现 "无感刷新"？用户填写表单时 Token 过期了怎么办？
    *   **A**: 利用 Axios 拦截器暂存失败的请求队列 (`failedQueue`)，Token 刷新成功后重放 (`replay`)。

## 2. 架构设计压力测试：千万级 PV 场景
**考察维度**：`高可用 (HA)`、`一致性模型`、`降级预案`

### Q2.1: 系统使用了 WebSocket 推送权限变更，如果 WS 连接数爆满（10w+）导致服务不可用，前端如何降级？
**考察点**：系统韧性设计。
**参考答案 (Rating: A)**：
1.  **自动降级**：当 WS 连接失败超过 3 次，自动切换为 "轮询 (Polling)" 模式（如每 60s 拉取一次）。
2.  **惰性检查**：在路由跳转 (`router.beforeEach`) 时才去校验指纹 (`ETag`) 或版本号。
3.  **S 级补充**：引入 "Jitter" (随机抖动) 重连机制，防止服务恢复瞬间被 10 万个客户端同时重连打挂。

### Q2.2: 页面使用了 CDN 缓存 HTML，如何防止用户看到旧的权限入口（如 "删除" 按钮）？
**考察点**：缓存策略与鉴权的冲突。
**参考答案 (Rating: S)**：
- **HTML 不缓存**：`Cache-Control: no-store`。
- **权限指令 (v-permission) 运行时求值**：即使 HTML 是旧的，Vue 组件 Hydration 后，`v-permission` 指令会根据 Store 中的最新权限（通过 API 获取）重新渲染 DOM，移除按钮。
- **边界 Case**：如果是由后端模板渲染的按钮（SSR），则必须在 Edge 节点（CDN 边缘函数）进行鉴权，或页面加载后立即发起一次 `check_permission` 请求进行修正。

## 3. 线上事故模拟：越权漏洞排查
**场景**：某天下午，运营群反馈 "实习生突然能看到【超级管理员】的菜单了"。

### Q3.1: 请给出排查路径。
**考察维度**：`Troubleshooting`、`日志分析`
**参考路径**：
1.  **前端排查**：检查 `permissionStore` 中的 `permissions` 数组是否包含了 `admin:*`。如果是，说明后端接口返回的数据有问题。
2.  **后端排查**：检查 API 日志，确认该用户的 `RoleID` 是否被错误修改。
3.  **中间件排查**：是否 Redis 缓存了错误的权限数据且未清理。
4.  **代码排查**：检查前端 `buildRoutes` 逻辑，是否写了 `if (true) routes.push(adminRoute)` 这种调试代码未删除。

### Q3.2: 紧急修复方案 (Hotfix) 是什么？
**考察维度**：`应急响应`
**参考答案**：
1.  **止血**：后端网关层立即拦截该实习生 UID 的所有写操作请求（Read-only mode）。
2.  **强制下线**：通过 WebSocket 发送 `force_logout` 消息，或后端使该用户的 Refresh Token 失效。
3.  **前端回滚**：如果是前端代码 Bug，利用 CDN 回滚 `index.html` 到上一版本。

## 4. 代码审查环节 (Code Review)
**考察维度**：`Vue 生命周期`、`内存泄漏`、`TypeScript`

请审查以下代码（模拟 `Permission.vue` 的错误实现）：

```typescript
// ❌ 错误示例
<script setup lang="ts">
import { usePermissionStore } from '@/stores/permission';
// 1. 必须在 setup 内部调用
const store = usePermissionStore();

// 2. 这里的判断只执行一次，Store 变更时不会响应
const hasAuth = store.permissions.includes(props.code);

// 3. 试图手动监听，但未销毁
window.addEventListener('storage', () => {
  console.log('权限变了');
});
</script>

<template>
  <!-- 4. 仅隐藏 CSS，DOM 还在，易被绕过 -->
  <div :style="{ display: hasAuth ? 'block' : 'none' }">
    <slot />
  </div>
</template>
```

**参考评审意见 (Rating: S)**：
1.  **响应性丢失**：`hasAuth` 必须是 `computed`，否则权限异步加载完成后，按钮仍不显示。
2.  **安全漏洞**：`display: none` 仅视觉隐藏，恶意用户可在控制台修改 CSS 显示按钮。应使用 `v-if` 将 DOM 从树中移除。
3.  **内存泄漏**：`window.addEventListener` 必须在 `onUnmounted` 中 `removeEventListener`。
4.  **TS 类型**：`props.code` 未定义类型，应使用 `defineProps<{ code: string }>()`。

## 5. 工程化深度
**考察维度**：`CI/CD`、`AST 分析`

### Q5.1: 如何在 CI 阶段阻止硬编码的权限字符串提交？
**参考答案**：
编写 ESLint 自定义规则或 Git Hook 脚本。利用 Babel/AST 解析所有 `v-permission="'xxx'"` 的值，与权限常量表（`constants/permissions.ts`）比对。如果发现未知字符串（如 `"admin:delete_USER"` 大小写错误），直接报错阻止 Commit。

### Q5.2: 权限变更如何做 Diff 检测？
**参考答案**：
在 `permissionStore` 更新时，对比 `oldPermissions` 和 `newPermissions`。
- **新增权限**：无操作（或 Toast 提示 "新功能已解锁"）。
- **减少权限**：关键！必须检查当前路由 `route.meta.permission` 是否在被删除的集合中。如果是，立即 `router.replace('/403')`。这比全量重置路由更高效。
