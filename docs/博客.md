# 从 0 到 1 设计一套前端鉴权与权限体系

### —— Vue + Axios 的一次完整工程化实践

> 鉴权不是一个功能，而是一套基础设施。
> 只有它稳定了，业务才能放心增长。

---

## 一、为什么我要重构前端鉴权方案？

在很长一段时间里，我对“前端鉴权”的理解非常简单：

*   登录成功 → 存 token
*   请求接口 → 带 token
*   401 → 跳登录页

直到问题开始不断出现：

*   **页面一刷新，Vuex/Pinia 里的 token 丢失**，用户被迫重新登录。
*   **Token 过期后，多个接口同时返回 401**，Refresh Token 接口被触发多次，导致服务器端 Token 轮换错误。
*   **权限改了**，但用户不刷新页面就还是能看到旧菜单，存在越权风险。
*   **Axios 拦截器越写越复杂**，业务代码到处是 `try...catch` 和异常判断。

这些问题单看都不致命，但叠加在一起后，**整个系统的登录态变得不可控**。

这也是我决定**系统性重构前端鉴权方案**的原因。

---

## 二、我踩过的 3 个典型坑

在讲最终方案前，我觉得有必要先说说我踩过的坑。

### 1️⃣ 把 Access Token 存在 localStorage

这是我早期最常见的做法，但问题很明显：

*   `localStorage` 对 JS 完全可读。
*   一旦发生 XSS（跨站脚本攻击），token 会被直接窃取。

后来我才意识到：**“方便”不应该建立在牺牲安全性的前提上。**

### 2️⃣ 只在 response 阶段处理 401

当时的逻辑是：

> 接口 401 → 刷新 token → 重试请求

但这意味着：请求已经失败了，再补救只是止损。而且，这种被动机制很难处理“并行请求”。

### 3️⃣ 并发请求各自刷新 Token

这是最危险的一个坑。

在某些页面初始化时（如 Dashboard），10+ 个接口同时发起。如果此时 Token 过期，所有接口几乎同时返回 401。
结果是：**前端发起了 10 次 `/refresh` 请求**。
如果后端实现了“Refresh Token 轮换（Rotation）”机制，第一个请求成功后旧 Token 即失效，剩下的 9 个请求全部报错，导致用户被强制登出。

**登录态彻底进入不稳定状态。**

---

## 三、我给这套鉴权方案定下的设计目标

在重构之前，我先给自己设定了几个明确目标：

*   **登录态可恢复**：页面刷新不是灾难，能自动恢复会话。
*   **Token 生命周期清晰**：Access Token (短效) + Refresh Token (长效/HttpOnly)。
*   **并发场景下行为确定**：无论多少请求并发，Refresh 只发生一次。
*   **权限与 UI 解耦**：避免硬编码，支持动态路由。
*   **实时性**：权限变更不仅要生效，而且要“立即”生效。

这不是“写几行拦截器”能解决的问题，而是一次**前端基础设施级别的设计**。

---

## 四、整体架构概览

最终我把系统拆成了三层核心模块：

```mermaid
graph TD
    A[Vue 应用 / 视图层] --> B[鉴权状态机 (Auth Store)]
    B --> C[Axios 调度中心]
    C --> D[后端 API]
    E[WebSocket 安全通道] --> B
```

在这套设计中，**Axios 不再只是请求工具**，而是整个登录态和鉴权流程的“调度中枢”。

---

## 五、核心设计一：用“鉴权状态机”管理登录态

我不再用“有没有 token”来判断登录状态，而是引入一个明确的状态机。

### 核心状态定义 (`src/auth/authTypes.ts`)：

```typescript
export type AuthStatus =
  | 'idle'          // 初始状态
  | 'bootstrapping' // 应用启动时检查认证
  | 'authenticated' // 已登录
  | 'expired'       // Token 过期，需要刷新
  | 'logged_out';   // 显式退出登录
```

### 为什么要这样做？

因为：

*   Token 只是状态的载体，不是状态本身。
*   页面刷新后，状态应该是“未知（Bootstrapping）”，而不是“未登录”。
*   所有请求都应该“服从”当前鉴权状态。

这一步，让登录态**从“零散逻辑”变成了“可推理系统”**。

---

## 六、核心设计二：让 Axios 服从状态机

这是整套方案中**技术含量最高**的一部分。我们在 Axios 拦截器之前，加了一层“调度”。

### 1️⃣ request 阶段：等待鉴权 ready

所有请求在发出前，都会先调用 `ensureAuthReady()`。如果当前状态是 `expired` 或正在刷新，**请求会被挂起等待**，而不是直接发出。

### 2️⃣ refresh 全局唯一 Promise (单例模式)

为了解决“并发刷新风暴”，我使用了一个模块级变量 `refreshPromise` 来保存当前的刷新请求。

代码实现 (`src/auth/refresh.ts`)：

```typescript
// Refresh Token 请求的单例 Promise
let refreshPromise: Promise<string | null> | null = null;

export async function ensureAuthReady(): Promise<string | null> {
  // 1. 如果已有 Token，直接返回
  if (authStore.isAuthenticated && authStore.accessToken) {
    return authStore.accessToken;
  }

  // 2. 关键：如果有正在进行的刷新请求，直接复用它！
  if (refreshPromise) {
    return refreshPromise;
  }

  // 3. 否则，启动新的刷新请求
  refreshPromise = refreshClient.post('/auth/refresh')
    .then(res => {
       // 更新 Store
       return res.data.accessToken;
    })
    .finally(() => {
      // 4. 无论成功失败，最后清理单例
      refreshPromise = null;
    });

  return refreshPromise;
}
```

### 3️⃣ refresh 使用独立 axios 实例

这是一个非常容易被忽略的细节。

Refresh 请求**不能使用主 axios 实例**。为什么？
因为主实例配置了拦截器，会拦截 401 并尝试刷新。如果 `/refresh` 接口本身也返回 401（Refresh Token 也过期了），就会触发死循环：刷新 -> 失败 -> 拦截 -> 刷新...

所以，必须创建一个干净的 `axios.create()` 专门用于刷新。

## 七、核心设计三：权限分层与动态路由

我最终采用了**三层权限模型**：

1.  **菜单权限**：控制 Sidebar 展示。
2.  **路由权限**：控制 `router.addRoute()`，未授权页面直接 404 或 403。
3.  **按钮权限**：控制具体操作（`v-if="hasPermission('user:add')"`）。

### 为什么不能只做前端权限？

因为**前端权限永远不可信**。用户可以在控制台手动修改 CSS 显示按钮，或者直接调用 API。
前端权限只用于**体验和引导**，真正的安全校验，一定在后端网关层完成。

---

## 八、核心设计四：权限如何做到“实时生效”？

一个常见但错误的做法是：
> 权限变更 → 提示用户刷新页面

这在体验和安全上都不可接受。如果管理员删除了某人的权限，他必须**立刻**失去访问能力。

我的做法是引入 **WebSocket 权限通道** (`src/permission/permissionChannel.ts`)：

1.  **建立连接**：登录后建立 WebSocket 长连接。
2.  **服务端推送**：当权限变更时，后端推送 `permission_change` 事件。
3.  **前端响应**：
    *   静默拉取最新权限数据。
    *   调用 `resetRouter()` 清空路由。
    *   调用 `buildRoutes()` 重建路由。
    *   **关键**：重新校验当前 URL。如果当前页面已无权限，直接重定向到 403。

整个过程用户无感知，但安全策略已实时更新。

## 九、这套方案带来的实际变化

上线后，这套鉴权方案带来了非常明显的变化：

*   **稳定性**：登录态相关 Bug 减少了 90%，不再有莫名其妙的掉线。
*   **体验**：用户几乎感知不到 Token 过期，静默刷新非常顺滑。
*   **安全**：权限修改不再依赖用户刷新，风险窗口期几乎为零。
*   **开发效率**：Axios 拦截器回归简单，业务代码不再需要处理 401。

**技术债明显下降。**

## 十、如果让我重来一次

有三件事我会更早做：

1.  **把鉴权当成“系统”，而不是功能**：一开始就要设计状态机，而不是堆 `if-else`。
2.  **不把权限信息塞进 JWT**：JWT 应该只存身份（Who are you），权限（What can you do）应该实时查询。一旦塞进 JWT，要在过期前撤销权限就很难了。
3.  **统一时间标准**：前端、后端、Token 的时间判断逻辑要统一，避免因客户端时间不准导致的提前/滞后过期。
